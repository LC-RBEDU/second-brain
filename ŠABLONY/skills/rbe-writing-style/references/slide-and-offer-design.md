# Slide and offer design

## Offer logic

A useful default for a compact offer is:

1. Name + claim
2. Context / what is happening for the client
3. Offer / what we propose
4. Offer / how it works, what is different, or the deeper layer
5. Investment / "Co si kupujete"

Do not force this structure when another architecture is clearly better. The more important rule is that every slide has a distinct job.

## Slide jobs

Typical distinct jobs include:

- Why this matters now
- What participants need to be able to do differently
- What experience/program we propose
- How the learning journey works
- What participants produce or practice
- What the client receives
- Investment / options
- Evidence / references

If two slides answer the same question, merge them or give one a new job.

## "Co si kupujete"

This is a recurring preferred slide. It should not be a prettier price list. It should translate money into value.

Good content types:

- preparation and tailoring
- facilitation / delivery
- participant outputs
- client outputs or artifacts
- follow-up / handout / recording / access when relevant
- named experts or co-facilitators when material
- scope difference between options

When two price variants exist, make the difference visible in what the client gets. Do not only say "half-day" versus "full-day".

Default granularity: often 3-4 bullets per option or 4 total value bullets, unless the task requires more.

## Concrete outputs

Prefer:

- "stakeholder map for the live case"
- "communication storyline ready to use with the team"
- "90-day experiment"
- "Critical Thinking Cheat Sheet"
- "prioritized project portfolio"

Over:

- "deeper understanding"
- "enhanced capability"
- "increased awareness"

Use learning outcomes when useful, but make the visible practice/output clear as well.

## Variants

Variants must differ in meaningful scope, depth, practice time, deliverables, or follow-up. Do not create cosmetic A/B variants that contain the same program with different labels.

## Slide length

Write for the slide, not for a document. Favor short bullets and strong hierarchy. If the content needs paragraph-length explanation, consider moving detail into speaker notes or a separate document only when the user asked for that format.
